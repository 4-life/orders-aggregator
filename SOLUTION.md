## Скидки в статистике

`daily-totals` отдаёт `gross`, `discount`, `net`; `total = gross` ([коммит](https://github.com/4-life/orders-aggregator/commit/3218082d8193f071f5dc3b9b1684eabb092489a8)).

- Миграция `002_discounts.sql`: колонка `orders.paid_kop BIGINT` (nullable) — фактически оплаченная сумма в копейках.
- `OrdersService.normalize`: принимает необязательные `discountPercent` и `amountPaid` (число или строка, как `amount`).
  `paidKop = toKop(parseRub(amountPaid))`; если поля нет — `paidKop = amountKop` (скидка 0).
- Проверка `amountPaid <= amount` — в zod-схеме (`refine`), нарушение → `ValidationError` (400 для вебхука, `invalid` в статистике синка).
- `OrdersRepository`: `paid_kop` пишется в `save`; при чтении `NULL` (строки до миграции) трактуется как `amount_kop`.
- `TotalsService.daily`: по каждому дню суммируются `gross` и `net` в копейках; `discount = gross - net`; в рубли — только на выходе.
  Так нет накопления ошибок float (`412.5`, а не `412.49999…`).

## Причина расхождения в марте

`TotalsService.daily` брал смещение таймзоны клиента один раз на текущий момент
и применял его ко всем заказам периода. В ночь на 29.03.2026 в европейских таймзонах переход на летнее время, поэтому
у заказов около полуночи день определялся со сдвигом на час и они попадали в соседний день.

Нашел потому что жалоба зависит от даты, а это либо сдвиг таймзон, либо переводы часов на летнее/зимнее. В коде new Date() - явный признак на ошибку (но не всегда).

Для исправления смещение считается для каждого заказа на момент его создания ([коммит](https://github.com/4-life/orders-aggregator/commit/a99de77586b550e4f068e1402c52e6ad2411b305)).

## Другие баги

- **`toKop` терял копейку.** `Math.floor(rub * 100)`: `4723.9 * 100 = 472389.99999999994` → `472389`.
  Среди реальных `amountPaid` из API таких значений 40 из 1937. Пока `amount` был целым в рублях, баг не проявлялся.
  Исправлено: перед `floor` погрешность снимается через `toFixed(4)`; отбрасывание долей копейки сохранено
  ([коммит](https://github.com/4-life/orders-aggregator/commit/be867065eb49cf7942578d73ac57409646ea5e73)).
- **Поведение внешнего API:**
  - `amount` и `discountPercent` иногда приходят строками (`"3100.00"`, `"10"`);
  - `createdAt` иногда без указателя зоны (`"2026-03-01T05:29:32"`) — уже обрабатывалось как UTC;
  - превышение лимита иногда приходит как `200` с `{ "error": "rate_limited" }` — уже обрабатывалось;
  - последняя страница — пустая с тем же курсором вместо `nextCursor: null` — уже обрабатывалось;
  - поля скидки есть только у заказов с 2026-03-15; у всех таких заказов есть оба поля сразу.
- **Ресинк не обновляет `paid_kop` у уже сохранённых заказов.** `apply()` пропускает версию, если `updatedAt` не новее
  сохранённой. На БД, заполненной до миграции, заказы со скидкой останутся с `paid = amount`. Для `result.json` (чистая БД) не влияет.

## Допущения

- `amountPaid` источник истины для `net`. Проверено на всех 1937 заказах со скидкой: `amountPaid` совпадает
  с `amount × (1 − discountPercent/100)` до копейки.
- Нет полей скидки значит скидка равна 0, `net = gross`.
- `amountPaid > amount` значит невалидный заказ (отклоняется, а не обрезается).
- Доли копейки отбрасываются, как и раньше в `toKop`.
- `total` = `gross` (по ТЗ).
